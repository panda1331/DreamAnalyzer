## 1. Цель тестирования
Проверить корректность работы бизнес-логики, API-эндпоинтов и взаимодействия с базой данных (PostgreSQL) в соответствии со спецификацией требований. Обеспечить изоляцию данных пользователей, стабильность обработки ошибок и достижение целевых показателей качества (NFR).

## 2. Области, подвергаемые тестированию (In-Scope)
*   **FR-01 — FR-05** (Модуль аутентификации: регистрация, логин, JWT, роли).
*   **FR-06 — FR-08** (Модуль снов: CRUD, изоляция данных).
*   **FR-09 — FR-13** (Модуль анализа: работа всех 5 стратегий).
*   **FR-16 — FR-18** (Админ-панель: управление пользователями и снами).
*   **FR-19 — FR-20** (Обработка ошибок, единый формат `ApiResponse<T>`).
*   **NFR-01** (Время отклика API ≤ 500 мс).
*   **NFR-07** (Покрытие кода модульными тестами ≥ 70%).

## 3. Области, НЕ подвергаемые тестированию (Out-of-Scope) с обоснованием
*   **NFR-02** (Время ответа AI ≤ 15 сек) — *исключено, так как скорость зависит от стороннего сервиса OpenRouter, а не от нашего кода (см. ISSUE-001).*
*   **UI/UX, верстка, адаптивность (NFR-05, NFR-06, NFR-11)** — *исключено на текущей итерации (ЛР3), будет тестироваться в рамках ЛР4.*
*   **Нагрузочное тестирование (NFR-01 при >100 пользователях)** — *исключено, будет проводиться на финальной стадии (ЛР5).*

## 4. Тестовая стратегия
Согласно заданию, описываем уровни (включая выполненные и будущие), виды и инструменты:
*   **Уровни тестирования:**
    *   *Модульное (Unit):* Покрытие сервисов и стратегий (xUnit, Moq).
    *   *Интеграционное (API/DB):* Проверка контроллеров через Swagger/Postman, связка с БД. 
    *   *Сценарное / Системное:* Сквозные сценарии через API. 
    *   *UI-тестирование:* Проверка интерфейса React, кроссбраузерность. 
    *   *Нагрузочное:* Проверка стабильности под нагрузкой. 
*   **Виды тестирования:** Функциональное (позитивное/негативное), регрессионное, тестирование безопасности (IDOR, JWT).
*   **Инструменты:** Swagger UI, Postman, xUnit, Coverlet, pgAdmin, VS Code / Visual Studio, браузер CMicrosoft Edge, JMeter.

## 5. Критерии тестирования (выраженные через метрики)
*   **Приёмочные (Acceptance):** 
    *   Все сценарии (UC-01 – UC-06) выполнены без блокирующих ошибок.
    *   Метрика успешного прохождения тест-кейсов (\(T_{SP}\)) **≥ 95%**.
    *   Метрика покрытия требований тест-кейсами (\(R_C\)) **≥ 90%**.
*   **Начала (Entry):** Код собирается без ошибок, БД развернута, секреты настроены.
*   **Приостановки (Suspension):** Если показатель успешного прохождения (\(T_{SP}\)) падает ниже 50% из-за блокирующего дефекта (например, не работает авторизация).
*   **Возобновления (Resumption):** После устранения блокирующего дефекта и выпуска фикса.
*   **Завершения (Exit):** Метрика выполнения тест-кейсов (\(T_E\)) равна **100%** (выполнены все 25 кейсов). Метрика устранения дефектов (\(D_{FTP}\)) для High и Critical равна **100%**.

## 6. Метрики (с формулами)
1.  **Процент успешного прохождения (\(T_{SP}\)):** `T_SP = (T_Success / T_Total) * 100%` (Цель: ≥ 95%).
2.  **Процент выполнения (\(T_E\)):** `T_E = (T_Executed / T_Planned) * 100%` (Цель: 100%).
3.  **Покрытие требований тест-кейсами (\(R_C\)):** `R_C = (R_Covered / R_Total) * 100%` (Цель: ≥ 90%).
4.  **Процент устранения дефектов (\(D_{FTP}\)):** `D_FTP = (D_Closed / D_Found) * 100%` (Цель: для High/Critical — 100%, для Medium/Low — ≥ 80%).
